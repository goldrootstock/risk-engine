# 코드 안내 — 흐름과 판단

코드를 줄 단위로 설명하지 않는다. 각 모듈이 **무엇을 하고 / 왜 이렇게 짰고 / 어디서 틀릴 수 있는지**를 적는다. 복습용이다. 파라미터 값의 근거는 `docs/decisions.md`, 설계의 배경은 `docs/design/`.

## 1. ETL — `risk_engine.data.etl`

### 무엇을 하나

세 공공 소스(ECB 환율, FRED 의 연준 H.15 국채 수익률, EIA 에너지 현물)에서 바이트를 받아, 표준 long 프레임으로 바꾸고, 계열별로 검증한 뒤, `prices`에 upsert하고, 무엇을 했는지 `etl_runs`에 한 행씩 남긴다. 명령은 `python -m risk_engine.data.etl sync|status`.

흐름은 다섯 단계가 직렬이고 단계마다 담당 모듈이 하나다.

```text
fetch (sources/*.py)  →  cache.store  →  parse (sources/*.py)  →  validate  →  load.upsert_prices
   bytes                 파일+manifest        long DataFrame        Report         LoadResult
                                                                        └─────── etl_runs 기록 (__main__ 만)
```

### 왜 이렇게 짰나

- **fetch와 parse를 분리**했다. 네트워크는 fetch 한 곳에만 있고, 캐시는 바이트를 저장하므로 `--offline`은 parse부터 다시 돈다. 픽스처 테스트는 네트워크 없이 parse만 검사한다. Java로 치면 `HttpClient`를 쓰는 클래스와 `Parser`를 인터페이스 경계로 나눈 것과 같다.
- **parse는 파일당 1회, long 형태.** ECB 파일 하나가 32통화라 계열마다 파싱하면 같은 zip을 12번 연다. long 형태(`source_id` 열)는 DB의 `prices` 모양과 같아 이후 단계에서 변환이 없다. 세 소스 모두 "내림차순 벤더 파일 → (source_id, price_date) 오름차순 + RangeIndex"로 끝나며, 이 정렬 계약은 하류 조인 사고를 막기 위한 것이라 테스트가 고정한다.
- **validate는 읽기 전용이고 커넥션을 받지 않는다.** 시그니처가 "검사가 대상을 바꾸지 않는다"(노트 00)를 강제한다. 결측을 채우거나 이상치를 자르는 코드는 ETL 어디에도 없다. 발견한 것은 `Finding`으로 돌려주고, 오케스트레이터가 error면 그 계열을 통째로 건너뛴다. 부분 적재는 나중에 결측처럼 보이는 구멍을 만들기 때문이다.
- **임계값은 return_type별로 다르다.** FX는 % 규칙, 국채는 bp, 에너지는 달러. WTI 2020-04-20(−36.98)이 그 이유다. 음수·0 근처 기준가로 % 를 계산하면 부호가 뒤집히거나 발산한다. 그날은 error가 아니라 warning으로 남아야 하고 테스트가 그것을 고정한다.
- **upsert는 값이 같으면 행을 건드리지 않는다.** `ON CONFLICT … DO UPDATE … WHERE … IS DISTINCT FROM`. 그래야 `loaded_at`이 "이 값이 마지막으로 바뀐 시각"을 뜻하고, `RETURNING (xmax = 0)`로 insert/update를 구분해 벤더 정정 건수(`rows_updated`)가 나온다. 정정 건수는 모델 문서의 데이터 품질 절 재료다.
- **ECB는 매번 전체를 다시 본다.** 절단하지 않고 84,000행을 매일 upsert한다. 가드 덕에 실제 쓰기는 정정 행뿐이고, `rows_unchanged ≈ 84,000`이 "전체를 재검증했다"는 증거가 된다. 재무부·EIA는 `start − 14일`부터만 받는다.
- **캐시는 덮어쓰지 않는다.** 파일명에 수집 시각과 sha가 있고, 같은 바이트면 manifest에 `same_as`만 남긴다. 벤더 재공시는 사실이라 흔적을 지우지 않는다. EIA 응답은 API 키를 에코하므로 fetch가 캐시 전에 지운다.
- **재시도는 헬퍼 하나.** `etl.http.fetch_with_retry`. 5xx·429·타임아웃만 재시도하고 4xx는 즉시 실패. `httpx.HTTPTransport(retries=N)`은 연결 실패만 재시도해 이 규칙을 못 담는다. 횟수·대기는 `RetryPolicy`(frozen)에 있고 값 고정 테스트가 잡고 있다.
- **exit code.** 스킵·실패가 1건이라도 있으면 2. 조용한 성공은 없다.

### 어디서 틀릴 수 있나

- **소스 형식 변경.** 재무부가 열 이름을 바꾸거나 ECB가 zip 구조를 바꾸면 parse가 깨진다. 404 HTML이 200으로 오는 경우도 있어 fetch가 본문 형식(`PK`, `Date`, JSON)을 검사한다. 픽스처는 2026-09-12 기준이라 형식이 바뀌면 `network` 마커 라이브 테스트로 잡는다.
- **달력 정렬은 여기서 안 한다.** DB에는 받은 날짜만 있다. 세 소스의 휴일이 달라 계열 간 날짜가 어긋나며, 정렬(intersection)은 수익률 빌더의 파라미터다. ETL 결과를 그대로 행렬로 쓰면 결측이 섞인다.
- **비동기 종가.** ECB 14:15 CET, 재무부 NY 15:30, EIA 일중. 같은 날짜라도 관측 시각이 달라 상관이 과소 추정된다. 모델 문서의 한계 절에 들어간다.
- **`--incremental`의 시작일은 소스 안 계열들의 `max(price_date)` 최솟값**이다. 한 계열이라도 적재된 적이 없으면 전체 이력으로 돌아간다. 새 계열을 유니버스에 추가한 날은 그 소스 전체가 전체 이력을 다시 받는다 — 의도된 안전 동작이다.
- **`etl_runs.source`는 적재 당시의 소스명**이다. 2026-09-13 이전 국채 적재 행은 `source='ustreasury'`로 남아 있어 `instruments.source`(`fred`)와 소스명으로 조인하면 붙지 않는다. `instrument_id`로 조인해야 한다 — 그래서 `etl_runs`에 `instrument_id`가 있다.
- **성공 기록은 가격과 같은 트랜잭션, 실패 기록은 별도 트랜잭션.** 성공 경로에서 `upsert_prices`와 `record_etl_run`을 하나의 `conn.transaction()`으로 감싸 가격과 감사 행이 함께 커밋되고, 기록이 실패하면 가격도 롤백된다. 실패 경로는 반대다. 롤백되는 트랜잭션 안에 실패 기록을 쓰면 그것도 사라지므로 블록 밖에서 따로 쓴다. `test_series_failure_leaves_no_prices_but_a_failed_run`이 고정한다.
- **FRED 절단 방지.** 응답의 `count`와 받은 관측치 수가 다르면 예외. `limit=100000`은 넉넉하지만 넘는 순간 조용히 잘리는 구조였다.
- **etl_runs는 series 단위**라 소스 전체가 fetch에 실패하면 그 소스의 모든 계열이 `failed`로 같은 사유를 갖는다. 어느 계열이 문제인지가 아니라 소스가 문제인 것이므로 정상이다.

### 첫 실전 실행에서 잡은 것 (2026-09-13)

세 가지가 테스트는 통과하고 실제 sync 에서만 드러났다. 픽스처·MockTransport 테스트의 한계를 보여 주는 사례라 남긴다.

1. **행 단위 upsert 는 30만 왕복.** 전체 이력 31 계열 ≈ 30만 행을 행마다 `INSERT … RETURNING` 으로 보내니 10분을 넘겼다. 노트 03 의 "10만 행 이상이면 COPY" 기준을 첫날에 넘긴 것이다. 임시 테이블에 `COPY` 로 밀어 넣고 `INSERT … SELECT … ON CONFLICT` 한 문장으로 병합하도록 바꿨다. 계열당 1.3 s.
2. **암묵 트랜잭션.** psycopg 3 는 autocommit 이 아니면 첫 SELECT 에서 트랜잭션을 열고, 그 뒤의 `conn.transaction()` 은 세이브포인트가 된다. "계열당 커밋" 이라고 믿었지만 실제로는 연결이 닫힐 때까지 아무것도 커밋되지 않았고, 도중에 죽으면 전부 사라졌다. sync 커넥션은 `autocommit=True` 로 두고 `conn.transaction()` 이 진짜 트랜잭션이 되게 했다. Java 로 치면 `Connection.setAutoCommit(false)` 상태에서 `commit()` 을 안 부른 것과 같다.
3. **재무부 WAF.** httpx 기본 UA·curl·설명형 UA 는 응답 없이 타임아웃, 브라우저 형식만 통과. 도구명을 Firefox 문자열의 괄호 안에 넣은 UA 로 통과시킬 수 있었지만 **채택하지 않았다** — 공개 저장소에 WAF 우회를 남기지 않는다. 같은 H.15 계보를 FRED 공식 API 로 받도록 소스를 교체했고, 겹치는 날짜 전부에서 값이 일치함을 확인했다(`docs/decisions.md`). 교훈: 기술적으로 가능한 것과 해도 되는 것은 다르다.
5. **키 유출 경로.** httpx 가 INFO 레벨로 요청 URL 전체를 찍고, httpx 예외 메시지도 URL 을 담는다. 로거를 낮추는 것은 증상 대응이라, EIA 키는 `X-Api-Key` 헤더로 보내고(응답 에코 때문에 스크럽은 유지), `etl.http` 가 예외 메시지에 경로만 넣도록 했다. FRED 는 쿼리 파라미터만 받으므로 이 두 장치가 유일한 방어선이다.
4. **EIA 의 `value: null`.** 일부 휴일 행이 `null` 로 온다. parse 가 그 행을 버린다(채우지 않는다).

### 증분 sync 의 휘발유 경고 (2026-09-13, JK 확인 요청)

두 휘발유 계열(NYH·USGC)이 **같은 날 2026-09-01** 에 각각 −0.347·−0.420 USD/gal 하락해 임계값 0.25 를 넘었다(NYH 3.550→3.203, USGC 3.863→3.443). 직전 관측은 두 계열 모두 2026-08-31 로 경과 1일 — 누적 변화가 아니라 하루 이동이다. 같은 날 두 계열 동시 하락이므로 데이터 오류로 볼 근거는 없다. **원인은 미확인**이다(계절 규격 변경 가설은 EPA 여름 RVP 기간이 9월 15일까지라 맞지 않아 철회). 임계값은 그대로 둔다. 이 확인을 계기로 `jump` finding 에 `prev_date`·`gap_days` 를 넣어 휴일·결측을 건너뛴 변화가 하루 점프로 읽히지 않게 했다.

### 면접 예상 질문

1. **"음수 유가는 어떻게 처리했나?"** — 데이터는 그대로 적재하고(사실), 검증은 return_type별로 분기했다. 에너지는 절대 변화 기준이라 −36.98은 jump warning으로 남지 경고 이상이 아니다. 수익률 정의도 절대 변화로 가서 FHS 시나리오가 물리적으로 불가능한 가격을 만들지 않게 했다. 로그수익률을 쓰는 FX에서 0 이하가 나오면 그건 error다.
2. **"매일 8만 행을 다시 upsert하는 게 낭비 아닌가?"** — `IS DISTINCT FROM` 가드 때문에 실제 쓰기는 정정된 행뿐이다. 대가는 비교 비용 몇 초이고, 얻는 것은 벤더 정정을 전부 잡고 `rows_updated`로 세는 것이다. ECB는 증분 엔드포인트가 XML뿐이라 파서를 하나로 유지하려고 전체 zip을 택했고, 캐시가 1 GB에 이르면 XML로 바꾼다.
3. **"검증이 결측을 채우지 않는 이유는?"** — 검증이 대상을 바꾸면 검증이 아니다. 채움은 모델 선택(수익률 빌더의 파라미터)이고 실행 기록에 남아야 한다. ETL이 조용히 채우면 나중에 어느 값이 벤더 값이고 어느 값이 우리 값인지 구분할 수 없다.
4. **"재시도 정책을 왜 frozen dataclass로 했나?"** — 실패를 보고 함수 안에서 횟수를 늘리는 코드를 못 쓰게 하려고. 값은 테스트가 고정해서 바꾸려면 테스트와 함께 커밋해야 한다. 같은 패턴을 λ·스트레스 충격·마진 플로어에도 쓴다.
5. **"API 키가 응답에 에코된다는 걸 어떻게 알았나?"** — 실제 응답을 캡처해 픽스처로 만들 때 `request.params.api_key`에 키가 그대로 있었고, 헤더로 보내도 마찬가지였다. 그래서 fetch가 캐시 쓰기 전에 바이트 수준에서 지우고, manifest의 URL은 쿼리스트링을 빼며, 예외 메시지도 경로만 담는다. gitignore에 기대지 않는다.
6. **"재무부 사이트가 막혔을 때 왜 우회하지 않았나?"** — 브라우저 형식 UA 로 통과하는 것을 확인했고 도구명도 넣을 수 있었다. 그러나 약관이 허용하는 것과 서버가 막는 것 사이에서, 공개 저장소에 우회 코드를 남기는 선택은 하지 않았다. 같은 H.15 데이터를 공식 API 로 제공하는 FRED 로 바꾸고, 겹치는 날짜 전부에서 값이 같음을 확인해 데이터 손실이 없음을 보였다. T+1 지연은 문서에 적었다.

## 2. 수익률 빌더 — `risk_engine.risk.{universe,levels,returns,pnl}`

### 무엇을 하나

DB 의 수준(가격·수익률)을 읽어 표본 집합에 맞춰 정렬하고, 계열 종류별 변화량 행렬 X(날짜 × 팩터)를 만든다. 포지션이 주어지면 X 의 한 행(또는 시나리오 n 행)을 USD P&L 로 바꾼다. 손실로 부호를 뒤집지 않는다 — 그건 ES/VaR 모듈 한 곳의 일이다.

```text
load_set("default")  →  load_levels(conn, tickers, start)  →  build(levels, specs)  →  pnl_matrix(X, levels_today, positions)
   universes.toml            읽기 전용 SQL, wide frame           ReturnMatrix              (n × 상품) USD, 부호 그대로
```

### 왜 이렇게 짰나

- **정렬은 수준 단계에서, 크로스는 정렬 뒤에.** FX 팩터 S_JPY = EURUSD / EURJPY 는 원계열 둘 중 하나만 결측이어도 못 만드니, 먼저 intersection 으로 날짜를 맞추고 그 뒤에 나눈다. 순서를 바꾸면 결측이 크로스에 전파된다.
- **FX 팩터는 "1 외화 = x USD".** 기준통화가 USD 인데 ECB 는 EUR 기준으로 준다. JPY 롱의 손익은 USD/JPY 가 정하지 EUR/JPY 가 정하지 않는다. 포지션 `EURJPY` 에 수량 q 는 q JPY 의 롱이고, `instruments.currency` 가 그 통화다.
- **변화량 종류가 셋인 이유는 P&L 매핑이 셋이기 때문이다.** 로그(FX)는 q·S·(e^x − 1) 정확식, 절대(에너지)는 q·x, bp(국채)는 −DV01·x. 표준화 잔차는 단위가 없어 공동 샘플링(같은 날짜의 z 를 함께 뽑기)이 종류가 섞여도 성립한다 — FHS 노트에서 쓴다.
- **DV01 은 매일 y 로 다시 계산한다.** CMT 수익률은 par 수익률이라 par 채권 수정 듀레이션 닫힌 식이 정확히 맞는다. y→0 에서 극한이 T 라 1M 의 0 % 도 안정. 컨벡시티는 1일 지평에서 0.5 % 미만이라 뺐고 스트레스에서 재검토.
- **`build` 와 `pnl_matrix` 는 순수 함수.** DB 를 모른다. `load_levels` 만 SQL 을 치고, 테스트가 `default_transaction_read_only` 세션에서 돌려 쓰기가 없음을 DB 가 보증한다(노트 00 §2 #4 의 형태를 처음 적용).

### 면접 예상 질문

1. **"금리에 로그수익률 대신 bp 차분을 쓴 이유는?"** — 0·음수 금리에서 로그가 정의되지 않고, 금리 리스크는 bp 충격 × DV01 로 사고하는 것이 관행이다(ISDA SIMM, FRTB 민감도). RiskMetrics 원문은 로그수익률을 썼지만 1990년대 금리 수준 전제다. 표준화 잔차는 단위가 없으므로 다른 종류와 섞어 공동 샘플링해도 문제없다.
2. **"DV01 을 고정하지 않고 매일 재계산하는 이유는?"** — 듀레이션은 금리 수준의 함수라 2020 년 0.6 % 와 2023 년 4 % 에서 다르다. par 채권 닫힌 식이라 비용이 없고, FHS 가 "오늘 조건" 으로 되돌리는 철학과 맞는다. 컨벡시티는 1일 지평에서 0.5 % 미만이라 뺐고 그 계산을 문서에 남겼다.
3. **"ECB 환율을 그대로 안 쓰고 USD 크로스로 바꾼 이유는?"** — 기준통화가 USD 다. EUR/JPY 를 팩터로 쓰면 JPY 포지션의 P&L 에 EUR 변동이 섞인다. S_CCY = EURUSD / EURCCY 로 정의하면 포지션이 외화 수량이 되고 P&L 이 USD 로 떨어진다.
4. **"휴일이 다른 소스를 어떻게 맞췄나?"** — 기본은 교집합이다. 채우기(ffill)는 채운 날 변화량이 0 이 되어 독립성 검정을 오염시키므로 옵트인이고 채운 수를 실행 기록에 남긴다. 교집합의 대가는 이틀치 변화가 하루로 합쳐지는 날이 생기는 것이고 그것도 기록한다.
5. **"부호는 어디서 뒤집나?"** — 여기서는 안 뒤집는다. P&L 은 P&L 이고, 손실 = −P&L 변환은 ES/VaR 모듈 한 함수에만 있다. 두 곳 이상에서 뒤집으면 언젠가 두 번 뒤집힌다.

## 3. FHS · Parametric · Monte Carlo — `risk_engine.risk.{volatility,measures,fhs,parametric,engine,record,positions}`

### 무엇을 하나

오늘의 포지션에 과거 변화량을 "오늘 변동성으로 다시 스케일해" 적용한 P&L 분포에서 VaR 99 %와 ES 97.5 %를 읽는다(FHS). 같은 공분산에 정규분포를 씌우면 Parametric, 정규분포에서 경로를 뽑아 정확한 매핑을 통과시키면 MC. 결과는 `risk_runs`(헤더)·`risk_measures`(지표 행)에 한 트랜잭션으로 기록된다.

```text
X (노트 04) ─ewma_variance─▶ σ_t ─▶ z_t = x_t/σ_t (워밍업 75 일 NaN)
                                  └▶ 최근 500 일 z 벡터 × σ_T ─pnl_matrix─▶ P&L (500 × 상품) ─to_loss─▶ VaR·ES·component ES
                                  └▶ 전체 풀의 250 일 창 전부 ─▶ ES 최대 창 = stressed_es
```

### 왜 이렇게 짰나

- **부호 반전은 `measures.to_loss` 한 곳.** 나머지 함수는 손실(양수)만 받는다. 이름(`loss`)이 계약이다.
- **z 는 out-of-sample.** σ_t 는 t−1 까지의 정보로 만든 예측이라 x_t/σ_t 가 진짜 표준화 잔차다. σ_T(오늘)는 마지막 행 다음의 예측(`sigma_next`)이고, 시나리오는 z_s × σ_T 다. "오늘 조건으로 되돌린 과거" 가 FHS 의 뜻이다.
- **잔차는 날짜별로 함께 뽑는다.** 2008-09-15 의 z 벡터는 31 개 팩터가 같은 날 함께 움직인 기록이다. 자산별로 따로 뽑으면 그 동시성이 사라지고 분산 효과가 과대 추정된다. 이것이 FHS 의 핵심 설계 선택이고 노트 05 §2-2 에 대안과 함께 적었다.
- **워밍업 75 일은 풀에도 백테스트에도 안 넣는다.** λ=0.94 에서 가중치의 99 % 가 74 일에 있으니, 75 일이 지나면 초기값의 흔적이 1 % 미만이다. 기본 집합에서 첫 FHS 가능일은 575 관측 뒤인 2008-06-13 이다 — 2007-08-16 은 풀에는 있지만 백테스트 표본에는 없다.
- **추정창과 풀은 다른 개념.** EWMA 는 창이 없고 유효 기억이 74 일이다(오늘 σ 를 정한다). 풀 500 일은 어떤 z 를 쓸지 정한다. 둘을 섞어 "500 일 EWMA" 라고 말하면 틀린다.
- **ES 는 Acerbi–Tasche 분수 가중.** n=500, α=0.975 면 12.5 개. 12 개 완전 가중 + 13 번째 절반. 상위 k 개 단순 평균은 k 가 정수가 아닐 때 편향된다. 컴포넌트 ES 는 같은 가중으로 상품별 손실 평균 — 합이 ES 와 정확히 같다(테스트).
- **stressed ES 는 현재 포지션 기준 최악의 250 일 창.** FRTB 가 요구하는 "이 포트폴리오에 가장 심각한 12 개월" 이다. 창 위치를 `params.stressed_window` 에 기록한다.
- **세 방법이 같은 X·같은 매핑·같은 손실 정의를 쓴다.** 그래서 Parametric 과 MC 의 차이 = 비선형성, MC 와 FHS 의 차이 = 분포 가정(정규 vs 경험)이 분리된다. 2026-09-09 MAIN: Parametric 0.88 M ≈ MC 0.89 M (선형 장부), FHS 1.09 M (두꺼운 꼬리, +24 %).

### 첫 실행 (2026-09-13, MAIN, as_of 2026-09-09, PV 177.3 M USD)

| 방법 | VaR 99 % | ES 97.5 % | stressed ES | 시나리오 |
|---|---|---|---|---|
| FHS (EWMA) | 1,093,925 (0.62 %) | 1,135,936 (0.64 %) | 2,731,909 (1.54 %) | 500 |
| Parametric | 883,197 | 887,546 | — | 500 (공분산) |
| MC (정규) | 886,626 | 892,987 | — | 10,000 |

### 어디서 틀릴 수 있나

- EWMA 는 레짐 전환 첫날에 늦다. 그 지연이 백테스트 초과의 주 원천이고, 백테스트 결과가 나쁘면 λ 를 바꾸지 않고 그대로 보고한다(노트 00 §3).
- 풀에 없는 사건은 못 만든다. W=500 이면 2008 은 2010 년 중반 이후 풀에서 사라지고 stressed ES 만 남는다.
- 잔차 평균이 0 이 아닐 수 있다(추세 구간). 재중심화하지 않고 평균을 `params.residual_mean` 에 기록한다.
- 컴포넌트 ES 는 시나리오 12.5 개의 평균이라 상품별로 잡음이 크다. 3주차의 자산군 집계가 더 안정적이다.

### 면접 예상 질문

1. **"FHS 에서 표준화 잔차를 자산별로 두나 전체를 묶나?"** — 자산별 σ 로 표준화하되 추출은 날짜별로 함께 한다. 잔차 벡터가 그날의 동시 움직임을 담고 있어야 포트폴리오 분산 효과가 역사대로 나온다. 전체를 한 풀에 섞으면 표본은 커지지만 종속성이 사라지고 WTI 의 −55 같은 꼬리가 FX 에 섞인다.
2. **"EWMA 초기값과 워밍업은 어떻게 정했나?"** — 초기값은 첫 75 일의 2 차 모멘트, 워밍업 75 일은 풀·백테스트에서 제외. 근거는 λ=0.94 의 99 % 가중이 74 일이라는 RiskMetrics 의 유효 일수다. 전체 표본 분산으로 초기화하면 미래 정보가 들어간다.
3. **"λ=0.94 의 추정창과 잔차 풀 500 일은 뭐가 다른가?"** — EWMA 는 창이 없고 유효 기억이 74 일이며 오늘의 σ 를 정한다. 풀 500 일은 어떤 잔차를 시나리오로 쓸지 정한다. 하나는 스케일, 하나는 모양이다.
4. **"ES 97.5 % 가 VaR 99 % 보다 작을 수 있나?"** — 있다. 정규분포에서는 거의 같고(2.34σ vs 2.33σ), 표본에서는 순서가 바뀔 수 있다. 같은 α 에서 ES ≥ VaR 만 보장된다. FRTB 가 97.5 % ES 를 고른 이유가 바로 정규 하에서 99 % VaR 과 같은 수준이면서 꼬리 모양을 반영하기 때문이다.
5. **"세 방법 결과가 다르면 어느 게 맞나?"** — 질문이 틀렸다. 셋이 같은 X 와 매핑을 쓰므로 차이의 원인이 분리된다: Parametric–MC 차이는 비선형성, MC–FHS 차이는 분포 가정. 그 분해 자체가 모델 문서의 내용이다.
