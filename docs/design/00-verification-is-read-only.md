# 설계 노트 00 — 검사·검증은 읽기 전용이다

- 상태: 원칙 확정 (2026-09-12, CI #1 실패의 사후 분석에서)
- 적용 범위: 저장소 전체. 각 모듈 노트가 이 노트를 참조한다.

## 0. 원칙

**검증 절차가 검증 대상을 바꾸면 그것은 검증이 아니다.** 검사(check)·검증(validate)·백테스트(backtest)·상태 조회(status) 함수는 발견한 것을 **반환**만 하고, 데이터·파일·DB·파라미터를 **바꾸지 않는다.** 상태를 바꾸는 동작은 별도의 이름(`fix`, `fmt`, `load`, `upgrade`, `fill`)을 가진 별도 명령이며, 사람이 그 결과 diff 를 보고 커밋한다.

## 1. 사례 — 이 원칙이 생긴 사건

CI #1(2026-09-12): 로컬 검사 루틴이 `ruff format .`(쓰기 모드)를 포함하고 있었다. 설계 노트 02 의 마크다운 Python 블록이 조용히 재포맷됐고, 그 변경은 커밋되지 않은 채 원격에 밀렸다. 로컬에서는 "통과"였고 CI 에서는 "실패"였다 — 검사가 대상을 고쳐 놓고 통과라고 말한 것이다. 조치: `make check` 는 `--check` 만, 훅은 검사만 하고 실패시킨다, `ruff`·`mypy` 버전 고정.

같은 날 코드에서 하나 더 찾았다: `migrate status` 가 `schema_migrations` 테이블이 없으면 **만들고** 나서 상태를 보고했다. 상태 조회가 DB 를 바꿨다. 조치: `applied_versions()` 는 `to_regclass` 로 존재만 확인, 테이블 생성은 `upgrade()` 만.

## 2. P1 에서 이 원칙이 깨질 수 있는 지점 (사전 목록)

| # | 모듈 | 깨지는 패턴 | 지켜야 할 형태 |
|---|---|---|---|
| 1 | ETL 검증 | 데이터 품질 검사가 결측·이상치를 **발견하고 채우거나 자른다** (forward-fill, winsorize, 음수 제거) | `validate(df) -> Report` 는 반환만. 적재는 받은 값 그대로(노트 01 §1). 채우기는 수익률 빌더의 **명시 파라미터**이고 `risk_runs.params` 에 기록된다 |
| 2 | ETL 캐시 | 재수집이 `data/raw` 의 이전 파일을 **조용히 덮어써** 오프라인 재실행이 다른 값을 본다 | 새 파일은 받은 날짜를 이름에 넣어 옆에 쓴다. 덮어쓰지 않는다. 변경 요약(행 수·달라진 값 수)을 로그로 남긴다 — 벤더 재공시는 **사실**이므로 흔적을 지우지 않는다 |

| 4 | 수익률 빌더 | 달력 정렬·결측 처리·이상치 클리핑이 **함수 안의 기본값**으로 조용히 적용된다 | 전부 명시 파라미터. 정렬 방식·채운 행 수·잘린 값 수를 반환값의 메타데이터에 싣고 `risk_runs.params` 로 간다. DB 에는 절대 쓰지 않는다 |

| 7 ⚠ | 스트레스 | 시나리오 충격 크기를 **목표 손실이 나오도록** 조정한다 | 충격은 역사적 사건 재현이거나 사전 명시된 가상 충격. 출처·날짜를 시나리오 정의에 기록 |
| 8 ⚠ | 마진 | 커버리지 백테스트가 99% 에 못 미치면 플로어·버퍼를 **사후 조정**한다 | 안티-프로시클리컬 파라미터는 규제 참조값(예: 25% 버퍼, 스트레스 창)으로 사전 고정. 조정은 별도 실행 + 모델 문서 변경 이력 |

## 3. ⚠ 세 항목 — "결과가 마음에 안 들어 입력을 바꾼다" (JK 지정, 2026-09-12)

#5·#7·#8 은 구조가 같다: 검증 결과를 보고 **검증 대상의 입력**(모델 파라미터·시나리오 충격·마진 플로어)을 고친 뒤 같은 표본에 다시 적용한다. 규제 검사(SR 11-7, FRTB 백테스트, CPMI-IOSCO)와 모델 검증에서 가장 심각하게 보는 유형이고, 사후 조정 자체보다 **조정 사실이 기록에 없는 것**이 문제다. 이름·규약이 아니라 코드 구조로 막는다.

| # | 구조적 방지 | 시그니처 |
|---|---|---|
| 5 | 백테스트 함수는 파라미터를 **불변 인자로만** 받고, 내부에 추정·최적화 루프가 없다. λ·창·신뢰수준은 `frozen=True` dataclass 로 들어오고 함수 안에서 재할당이 불가능하다. 파라미터의 해시가 `backtest_results` 에 기록되어 "어느 설정으로 검정했나"가 결과와 분리될 수 없다. 대안 파라미터는 **새 실행**(`tag='experiment'`)이지 기존 실행의 재검정이 아니다 | `backtest(runs: Sequence[RunRecord], realised: PnLSeries, cfg: BacktestConfig) -> BacktestReport` — DB 를 쓰는 함수는 별도 `record(report) -> int` 하나 |
| 7 | 시나리오 충격은 **버전 관리되는 설정 파일**(`config/stress_scenarios.toml`)에서만 온다. 코드는 파일을 읽어 `frozen` 객체로 만들고 파일의 sha256 을 `risk_runs.params.scenario_set` 에 기록한다. 충격을 인자로 받는 함수는 있어도 충격을 **계산해서 만드는** 함수는 없다(역사적 재현은 날짜 구간을 지정할 뿐 크기를 정하지 않는다) | `stress(portfolio: Positions, scenarios: ScenarioSet) -> StressReport` |
| 8 | 플로어·버퍼·스트레스 창은 `config/margin_params.toml` 에서만 오고 sha256 이 실행에 기록된다. 커버리지 백테스트는 마진 실행 결과를 **읽기만** 하고 파라미터 객체를 받지 않는다 — 파라미터를 바꿔 다시 돌리려면 새 마진 실행을 만들어야 하고 그 실행은 다른 해시를 가진다 | `coverage_backtest(margin_runs: Sequence[MarginRun], realised: PnLSeries) -> CoverageReport` |

공통 장치: 설정 파일 → 해시 → 실행 기록. 어떤 실행이 어떤 입력으로 나왔는지가 결과 행에 붙어 있으면, 사후 조정은 막히는 것이 아니라 **보이게** 된다. 그것이 규제 검사가 요구하는 형태다.

각 모듈 노트(02 ETL, 03 fetcher, 04 수익률, 이후 백테스트·마진)는 자기 행의 "지켜야 할 형태"를 인터페이스 시그니처로 옮긴다: 검증 함수는 `-> Report`, 변경 함수는 `-> Result` 에 변경 건수를 싣는다.
